How a claim gets processed

A claim is one patient transfer: every file that belongs to it — face sheet, ePCR, PCS, booking summary — uploaded together. Each file is read on its own, then the claim combines what they found. This page walks through that pipeline stage by stage, what each claim status and tag actually means, and the questions that come up most.

The unit of work

What counts as one claim

A single ambulance transport rarely arrives as one document. The Claims tab treats every file from the same transfer as one claim: upload them together, and each is OCR'd and extracted on its own, then the results are combined into a single set of fields and a single set of tags for the whole transfer.

One bad file never sinks the bundle. If a file fails to upload — wrong format, unreadable — it's listed as rejected and every other file in the claim still goes through. A claim only gets refused outright if every file in it was rejected.

Stage by stage

What happens after you upload

Upload

Pick every file for the transfer and submit. The claim is created immediately with each file's accept/reject result; processing happens in the background from here, so the page doesn't wait for it.

OCR

Each file is read independently — a real text layer in a PDF is used directly when one exists; a scanned page is recognized character by character. This runs entirely on this network.

Extract & normalize

A local model reads the recognized text and pulls out fields — name, DOB, insurance, run number, physician, and the rest. Nothing is trusted on the model's word alone: every value has to actually appear on the page before it's kept, or it's dropped rather than guessed at.

From there each value is typed into the shape that gets entered downstream — phone numbers, SSNs, dates. A date of birth written with a 2-digit year ("12/19/53") doesn't get parsed on a blind convention: it's checked against a printed age or the visit date on the same page to land on the right century, not just the nearer one.

Merge across the claim

Once every file in the claim has finished its own pass, the claim combines them field by field. The face sheet wins on demographics and insurance, the ePCR wins on trip and clinical detail, the PCS wins on the physician and medical necessity — but that's only a tiebreaker. A real answer found on any file always beats a placeholder default from the "preferred" one, and a reviewer's correction always wins outright, no matter which file it was made on.

Auto-tag

The merged claim is checked against every rule that can be expressed deterministically from TAGS.docx. A tag that fires records exactly which document, page, and field triggered it, so it's never a black box — see reading a tag below.

Review

Open the claim to see its documents, its tags, and anything flagged for manual review. Dismiss a tag that doesn't apply, add one the rules couldn't catch, correct a field by hand, or reprocess the whole claim if something changed.

Status

What a claim's status means

StatusMeaning
Pending Uploaded; processing hasn't started on it yet.
Processing At least one document in the claim is still being OCR'd or extracted.
Completed Every document in the claim finished successfully. Ready for review.
Partial Some documents finished, at least one didn't. The claim is still tagged and mergeable from whatever did complete.
Failed No document in the claim reached a usable result. Reprocess once the underlying issue (a bad scan, an unreachable model) is resolved.

Evidence, not a guess

Reading a tag

Every tag on a claim comes from TAGS.docx — that document is the single source of truth for which tags exist and why. A chip on the claim looks like this:

Wheelchair transport 1.00 ← tag name and confidence
Name
The tag as printed in TAGS.docx.
Confidence
The grounding confidence of the weakest fact the rule relied on — 1.00 for an exact match on the page, 0.70 for a fuzzy one. Not a guess about whether the tag is right; a measure of how directly its evidence was found.
Evidence
Which document, page, and field actually triggered the rule.
Reason
The SOP language from TAGS.docx explaining why the tag exists at all.
Manual review
A tag with no rule able to fire on it yet — usually because it depends on a reference sheet or judgment call the system doesn't have. Shown with its SOP reason so it can be judged by hand and added if it applies.

Common questions

FAQ

A tag I expected isn't there — why?

Either the rule for it needs data the claim doesn't have yet (check the manual-review list for it), or the field it depends on wasn't found on any page in the claim. Add it by hand from the tag list if you're sure it applies — that addition survives even if the claim is reprocessed later.

The claim says "partial" — what should I do?

At least one file in it didn't finish. The claim is still usable from whatever did complete, but check the document list for the one that failed and reprocess it once whatever caused it (a bad scan, a connectivity issue) is resolved.

One file got rejected on upload — is the whole claim lost?

No. A rejected file is listed with its reason and the rest of the claim proceeds normally. The claim only fails to create if every file in it was rejected.

I corrected a field by hand — will reprocessing undo it?

No. A manual correction always outranks anything reprocessing would compute, on that field, from that point forward.

Can new tags be added without a code change?

Yes, for any tag whose condition can be written as a rule. Adding one is an edit to the rules file that sits alongside TAGS.docx — no application changes needed. A tag that genuinely needs judgment or a reference sheet the system doesn't have stays in manual review instead.
